Flight Delay Predictor — How It Was Built

An end-to-end ML project: data to model to API to deployment, with the real decisions and trade-offs behind it.

1. Problem & Data

Binary classification: predict whether a US domestic flight departs 15+ minutes late (DEP_DEL15), using the Kaggle dataset 2019 Airline Delays and Cancellations (~3M+ flight records).

2. Feature Engineering

Rather than using the dataset's built-in historical columns (which risk leakage from future information), historical delay averages were self-computed from the training data: carrier, airport, day-of-week, and time-block average delay rates.

Categorical variables (carrier, airport, time block) were encoded via .cat.codes rather than one-hot encoding, appropriate for a tree-based model that doesn't need linear-friendly encodings and handles high-cardinality categories natively.

Class imbalance (~19% delayed) was addressed via scale_pos_weight in XGBoost, rather than resampling, keeping the full dataset intact while correcting the loss function's bias toward the majority class.

3. The Feature-Scoping Decision (v1 to v2)

The first model (v1) used 21 features, including PLANE_AGE, CONCURRENT_FLIGHTS, monthly flight-volume counts, and PREVIOUS_AIRPORT.

Once building the live prediction API, a key question surfaced: could a real user actually provide these inputs? The answer was no. These fields require either aircraft-tracking infrastructure (tail number history, live traffic counts) or data no free/public API exposes.

Rather than silently imputing placeholder values for unavailable inputs, which would quietly degrade prediction integrity, the model was retrained on 15 features, keeping only what a user can realistically provide or what can be reliably sourced live (weather API, precomputed historical priors).

Performance was effectively unchanged after dropping 6 features, evidence they carried little marginal signal beyond the historical priors. Deployability was prioritized over marginal feature completeness, without sacrificing accuracy.

4. Interpretability & Error Analysis (SHAP)

SHAP (TreeExplainer) was used to understand which features drive predictions. DEP_TIME_BLK (scheduled departure time window) emerged as the most decisive feature, consistent with real airline operations, since delays cascade through the day as aircraft and crew schedules compound.

Manual error analysis on the confusion matrix revealed a concrete pattern:

  • False positives (flagged delayed, actually on-time) cluster in evening time blocks, with high historical time-block delay rates and worse-than-average weather.
  • False negatives (missed real delays) cluster in morning time blocks, with low historical delay rates and good weather. Delays here come from causes the model has no signal for (mechanical, staffing, one-offs).
Conclusion: the model over-relies on time-of-day as a proxy signal. Documented as an honest, known limitation rather than hidden, and a legitimate direction for a future v3 (feature interactions, threshold tuning).

5. Live API & Enrichment

The API (FastAPI) only asks users for what they'd actually know about their flight: month, day of week, departure time block, distance group, carrier, and departing airport.

Everything else is fetched automatically, server-side:

  • Live weather, via the Open-Meteo API, using a coordinate lookup table for the 96 airports the model supports
  • Historical priors, precomputed carrier/airport/day/time-block average delay rates, looked up from saved reference tables

Unknown carriers or airports (outside the training vocabulary) are explicitly rejected with a clear error, rather than silently mispredicting, a deliberate integrity decision consistent with the feature-scoping choice above.

7. Known Limitations (documented honestly)

  • 96-airport scope: the model can only predict for airports present in the 2019 training data, a structural limit of categorical encoding, not fixable by fetching live data for new airports.
  • Precision (0.33): roughly 1 in 3 flights flagged as delayed are false alarms, documented as an honest baseline, tied to the time-of-day over-reliance found in error analysis.
  • Weather fallback: if Open-Meteo is unreachable, the API falls back to neutral default weather values rather than failing the request entirely, noted here for transparency.
  • Deployment uptime: hosted on a manually-managed VM (Azure Student credits), not an always-on production service. May be offline between demo sessions.
